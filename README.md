# databy.ai

databy.ai is an AI-powered database workspace for exploring SQLite and PostgreSQL data with a natural-language assistant or a SQL Runner. It includes a FastAPI backend, React/TypeScript frontend, SQLite application storage, authenticated connection and execution APIs, LangGraph orchestration, deterministic analytics, query history, and saved queries.

## Technology stack

- **Backend:** Python 3.11+, FastAPI, SQLAlchemy 2.x, Pydantic, SQLite, Alembic, Uvicorn
- **Authentication:** Argon2 password hashing and signed JWT access tokens
- **SQL generation:** LangChain, `langchain-groq`, Groq API, SQLGlot
- **Frontend:** React, TypeScript, Vite, Tailwind CSS, React Router, Recharts, Lucide React
- **AI orchestration:** LangGraph conditional workflow, structured Groq outputs

## Prerequisites

- Python 3.11 or newer
- Node.js 20.19+ or 22.12+
- npm

## Environment configuration

From the project root, copy `.env.example` to `.env` and adjust values if needed:

```powershell
Copy-Item .env.example .env
```

`.env` is ignored by Git. Do not commit credentials or secrets.
For local development, set `JWT_SECRET_KEY` to a random value, for example:

```powershell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

The development fallback is not accepted in production. Production also requires a valid Fernet key for stored PostgreSQL credentials and explicitly configured HTTPS CORS origins (an empty value disables cross-origin access for a same-origin deployment). Generate the encryption key with:

```powershell
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Keep both generated secrets in the deployment secret manager or an untracked `.env`; do not commit or log them. `GROQ_API_KEY` is optional, but natural-language SQL generation and LLM intent classification require it.

## Internal application database

The backend's SQLite database is exclusively for databy.ai application records: users, registered connection metadata, conversations, messages, query history, saved queries, approvals, and audit logs. It is stored by default at `backend\data\databy_ai.db`. The `DATABASE_URL` setting can point to another SQLite path. User-connected databases are stored and accessed separately. PostgreSQL passwords are encrypted at rest; SQLite upload records contain only a generated file key.

Alembic is the only schema migration mechanism. From `backend`, run:

```powershell
.\.venv\Scripts\alembic.exe upgrade head
```

After changing SQLAlchemy models, create and apply a migration:

```powershell
.\.venv\Scripts\alembic.exe revision --autogenerate -m "describe schema change"
.\.venv\Scripts\alembic.exe upgrade head
```

Review autogenerated migrations before applying them. Tests migrate a separate temporary SQLite database and do not use the development database.

## Authentication API

- `POST /api/v1/auth/register` — create an account with `username`, `email`, and a password of at least 12 characters.
- `POST /api/v1/auth/login` — authenticate with `email` and `password`; returns a bearer access token.
- `GET /api/v1/auth/me` — return the authenticated account (requires `Authorization: Bearer <access_token>`).

Passwords are stored as Argon2 hashes, and access-token lifetime is controlled by `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` (30 minutes by default). Login and registration requests are rate limited per client IP in each backend process (`AUTH_LOGIN_RATE_LIMIT`, `AUTH_REGISTER_RATE_LIMIT`, and `AUTH_RATE_LIMIT_WINDOW_SECONDS`). Password fields and hashes are excluded from user responses; validation errors omit submitted field values.

Example registration and login using PowerShell:

```powershell
$user = Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/api/v1/auth/register `
  -ContentType "application/json" `
  -Body '{"username":"demo-user","email":"demo@example.com","password":"Replace-this-password-123"}'

$tokenResponse = Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/api/v1/auth/login `
  -ContentType "application/json" `
  -Body '{"email":"demo@example.com","password":"Replace-this-password-123"}'

Invoke-RestMethod -Uri http://localhost:8000/api/v1/auth/me `
  -Headers @{ Authorization = "Bearer $($tokenResponse.access_token)" }
```

## User database connections

Phase 4 supports uploaded SQLite (`.db`, `.sqlite`, `.sqlite3`) and external PostgreSQL connections. Every connection endpoint requires a bearer access token. From a successful login, set the token in PowerShell:

```powershell
$headers = @{ Authorization = "Bearer $($tokenResponse.access_token)" }
```

Upload SQLite with multipart form data:

```powershell
Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/api/v1/connections/sqlite/upload `
  -Headers $headers `
  -Form @{ name = "Local analytics"; file = Get-Item .\analytics.sqlite3 }
```

SQLite uploads are size-limited by `MAX_SQLITE_UPLOAD_SIZE_BYTES` (50 MiB by default), verified for format and integrity, assigned a server-generated filename, and inspected read-only. WAL-mode database files are rejected because a single-file upload cannot safely include their separate WAL state; checkpoint the database and provide a standalone SQLite file before uploading. Files are stored under `SQLITE_UPLOAD_STORAGE_DIR` (default `backend\data\uploads`).

Create a PostgreSQL connection by sending `name`, `host`, `port`, `database_name`, `username`, `password`, and optional `sslmode` (`require` by default) as JSON to `POST /api/v1/connections/postgresql`. The server tests the connection before saving it. `POST /api/v1/connections/postgresql/test` tests the supplied details without saving them. Passwords are encrypted using Fernet and never returned by the API.

Generate a Fernet encryption key and set it as `POSTGRES_CREDENTIALS_ENCRYPTION_KEY` in `.env`:

```powershell
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

If the key is not configured or is invalid, saving PostgreSQL credentials fails closed. Keep the key stable and back it up securely; changing or losing it makes already-encrypted connection passwords unreadable. `DATABASE_CONNECTION_TIMEOUT_SECONDS` configures PostgreSQL connect and pool timeouts.

Connection endpoints:

- `POST /api/v1/connections/sqlite/upload`
- `POST /api/v1/connections/postgresql/test`
- `POST /api/v1/connections/postgresql`
- `GET /api/v1/connections` and `GET /api/v1/connections/{connection_id}`
- `POST /api/v1/connections/{connection_id}/test`
- `GET /api/v1/connections/{connection_id}/schema`
- `DELETE /api/v1/connections/{connection_id}`

Schema inspection returns accessible schema/table names, columns and types, nullability, primary/foreign keys, unique constraints, and indexes. It does not retrieve table rows or execute user-provided SQL. PostgreSQL connections use a bounded pool and configured connection timeout. In hosted deployments, restrict outbound network access to prevent connections to internal services.

The Database Connections page uses the login access token in memory only. Paste the token from the login response into the page; it is not saved in browser storage and is cleared by a page refresh.

## SQL generation and validation

Phase 5 adds authenticated SQL generation and validation endpoints. Set `GROQ_API_KEY` in `.env`; `GROQ_MODEL` selects the Groq model (default: `openai/gpt-oss-120b`), and `GROQ_TIMEOUT_SECONDS` bounds provider requests. The configured model must be enabled for your Groq account; check the current [Groq supported models](https://console.groq.com/docs/models) before deployment. Generation uses a low temperature and structured Pydantic output.

```text
POST /api/v1/connections/{connection_id}/generate-sql
POST /api/v1/sql/validate
```

Both require the user's bearer access token and enforce connection ownership. Generation passes only the natural-language question, target dialect, and bounded schema metadata to the model. It does not send database credentials, tokens, or table rows. If the schema exceeds the configured context limit, it is not silently truncated; the service narrows to schema-matched tables and their direct foreign-key neighbors, or asks for clarification.

Generated SQL is parsed using the connected database's SQLGlot dialect and checked for read-only query shape, a single statement, blocked write/admin/session/locking operations, dangerous functions, and unknown or ambiguous schema identifiers. SQLite and PostgreSQL are supported. These checks are conservative safeguards, not a guarantee of query cost or complete security; SQLGlot does not make arbitrary SQL safe to execute.

SQL execution is restricted to the separate, bounded read-only execution API described below.

Relevant environment settings:

- `GROQ_API_KEY` and `GROQ_MODEL`
- `GROQ_TIMEOUT_SECONDS` (default 20)
- `SQL_GENERATION_MAX_ATTEMPTS` (default 2; only malformed structured responses are retried)
- `SQL_GENERATION_MAX_QUESTION_CHARS` (default 2000)
- `SQL_GENERATION_MAX_SCHEMA_CHARS` (default 24000)
- `SQL_MAX_QUERY_CHARS` (default 10000)

To try generation, log in to receive an access token, then submit a question:

```powershell
Invoke-RestMethod -Method Post `
  -Uri "http://localhost:8000/api/v1/connections/<connection-id>/generate-sql" `
  -Headers @{ Authorization = "Bearer $token" } `
  -ContentType "application/json" `
  -Body '{"question":"Show the five customers with the most orders"}'
```

To validate SQL without executing it:

```powershell
Invoke-RestMethod -Method Post `
  -Uri http://localhost:8000/api/v1/sql/validate `
  -Headers @{ Authorization = "Bearer $token" } `
  -ContentType "application/json" `
  -Body '{"connection_id":"<connection-id>","sql_query":"SELECT name FROM customers LIMIT 5"}'
```

Tests use mocked Groq model responses and require no Groq API key.

## Safe SQL execution

Phase 6 adds a real, bounded read-only execution engine for connected SQLite and PostgreSQL databases:

- `POST /api/v1/connections/{connection_id}/execute` accepts `sql_query`, optional `page_size`, `offset`, and an optional owned `conversation_id`.
- `GET /api/v1/executions/{execution_id}` returns the result while its short-lived result window is cached, or execution metadata after the result expires.

Execution always checks authentication and connection ownership, inspects the actual external schema, and reruns the SQLGlot validator immediately before execution. The frontend's separate validation request is only a usability aid and is never trusted by the execution endpoint. Invalid and write SQL is rejected and recorded in query history; no write execution is implemented.

SQLite target engines open uploaded files read-only and use `query_only`, `trusted_schema=OFF`, a progress handler for timeout interruption, and a bounded pool wait. PostgreSQL execution starts a read-only transaction and sets a per-query `statement_timeout`; the transaction is rolled back before returning the pooled connection. Use a least-privileged, read-only database account for PostgreSQL where possible—AST checks and read-only transactions are defense-in-depth, not a guarantee against every side effect from custom database functions.

Rows are fetched in bounded batches. Results stop at the row or response-size limit and mark `truncated`; duplicate column names receive stable unique labels. Values such as dates, timestamps, decimals, UUIDs, bytes, nulls, and non-finite floats are serialized safely. Database driver errors are not returned to clients.

Only execution metadata and SQL/status/duration are persisted in the existing `query_history` table; result rows are never written to the application database. SQL string/numeric literals and comments are redacted from stored history. Result windows are cached in process memory with bounded size, entry count, and TTL. They are lost on process restart and expire after `SQL_EXECUTION_RESULT_CACHE_TTL_SECONDS`; after that, the GET endpoint returns metadata and indicates that result rows expired. The cache is process-local, so deployments with multiple workers do not share result windows.

Execution limits are configured in `.env`:

- `SQL_EXECUTION_TIMEOUT_SECONDS` (default 5)
- `SQL_EXECUTION_DEFAULT_PAGE_SIZE` (default 100)
- `SQL_EXECUTION_MAX_PAGE_SIZE` (default 500)
- `SQL_EXECUTION_MAX_OFFSET` (default 100000)
- `SQL_EXECUTION_MAX_COLUMNS` (default 100)
- `SQL_EXECUTION_MAX_RESULT_BYTES` (default 2097152 / 2 MiB)
- `SQL_EXECUTION_MAX_CONCURRENT_PER_USER` (default 2; enforced per application process)
- `SQL_EXECUTION_RESULT_CACHE_TTL_SECONDS` (default 900)
- `SQL_EXECUTION_RESULT_CACHE_MAX_BYTES` (default 33554432 / 32 MiB)
- `SQL_EXECUTION_RESULT_CACHE_MAX_ENTRIES` (default 500)

The responsive SQL Runner is available at `/sql-runner`. It uses real connection, validation, and execution API responses; after logging in, select a connection, validate, then execute.

## LangGraph AI assistant

The `/assistant` page runs a real conditional LangGraph workflow over persisted conversations. These authenticated endpoints create and list conversations, retrieve a conversation's messages, and stream assistant replies:

- `POST /api/v1/assistant/conversations`
- `GET /api/v1/assistant/conversations`
- `GET /api/v1/assistant/conversations/{conversation_id}`
- `POST /api/v1/assistant/conversations/{conversation_id}/messages` (Server-Sent Events)

For data questions, the graph classifies intent, checks connection ownership and retrieves its schema, reuses the existing SQL generator, independently validates its output, executes only through the read-only execution service, analyzes the bounded results locally, and returns a grounded summary. Schema exploration, general questions, clarification, and unsupported requests take different routes. Every request revalidates SQL before execution; write operations remain unavailable.

SSE progress events contain only completed workflow steps, not private chain-of-thought, prompts, credentials, or database connection details. SQL execution results are not sent to Groq; the assistant summarizes bounded returned data in-process. Conversation messages and query metadata persist in the internal SQLite database; complete result sets are not persisted. Recent conversation context is bounded to 12 messages and 6,000 characters. LangGraph is invoked per message without a checkpointer because the existing conversation/message records are the durable history; workflow state is request-scoped.

Set `GROQ_API_KEY` before using AI classification or SQL generation. The assistant frontend and API require a bearer access token, and the token is kept in browser memory only.

## Analytics and visualizations

Successful execution results can be analyzed while their bounded result window remains in the existing process-local cache. The analytics service performs local deterministic calculations (numeric minimum, maximum, mean, median, total; null and distinct counts; bounded category frequencies; date ranges and grouped trends). Statistics describe only the rows returned by the execution and display a truncation notice when the result window was bounded. No result rows are persisted for analytics or sent to Groq.

Authenticated analytics endpoints:

- `GET /api/v1/executions/{execution_id}/analytics` — per-column statistics, category/date summaries, grouped results, and observations.
- `GET /api/v1/executions/{execution_id}/charts` — suitable chart recommendations with explicit field mappings and chart-ready data for bar, line, pie, area, and scatter visualizations.
- `GET /api/v1/executions/{execution_id}/export/csv` — downloads the cached result as UTF-8 CSV; formula-like text cells are prefixed to prevent spreadsheet formula injection.
- `POST /api/v1/executions/{execution_id}/analytics/follow-up` — answers supported average, distribution, highest-group, and monthly questions using only cached returned rows. Unsupported questions can be continued in the AI Assistant, where any new query uses the existing generation, validation, ownership, and read-only execution flow.

All endpoints verify execution and connection ownership. Analytics, charts, follow-ups, and CSV export do not rerun SQL. Once results expire or are unavailable, the endpoints return an explicit error and users must execute a query again. Chart recommendations are conservative and omitted when the result shape is unsuitable.

Both the AI Assistant and SQL Runner provide Table, Charts, and Analytics Summary views, plus CSV export and cached-result follow-up questions. Visualization is rendered with Recharts and operates only on the already-bounded results. The frontend test suite runs with:

```powershell
Set-Location frontend
npm.cmd test
```

## Workspace history and saved queries

The authenticated frontend provides account registration and login, a data-backed dashboard, a schema explorer, SQL Runner, AI Assistant, query history, saved queries, analytics, and account settings. The bearer token is kept in the current browser session and cleared on sign-out or an unauthorized response.

Workspace metadata endpoints:

- `GET /api/v1/history?page=1&page_size=20&status=succeeded&search=...` — paginated execution metadata. Status and search are optional. SQL literals have already been redacted; execution result rows are not stored in history.
- `GET /api/v1/saved-queries?search=...` — list the current user's saved SQL.
- `POST /api/v1/saved-queries` — save `{ "connection_id": "...", "name": "...", "description": "...", "sql_query": "..." }`.
- `PATCH /api/v1/saved-queries/{saved_query_id}` — update saved query details or SQL.
- `DELETE /api/v1/saved-queries/{saved_query_id}` — delete a saved query.

All of these endpoints require authentication and enforce user/connection ownership. Saved SQL is always revalidated by the existing read-only SQL pipeline when submitted for execution. The Analytics page can inspect recent successful result windows; expired results are reported rather than rerun.

## Production readiness and deployment

### Production configuration

Set `APP_ENV=production`, a random `JWT_SECRET_KEY` of at least 32 characters, a valid `POSTGRES_CREDENTIALS_ENCRYPTION_KEY`, `POSTGRES_ALLOWED_HOSTS` to a comma-separated exact hostname/IP allowlist, and `CORS_ORIGINS` to the exact HTTPS frontend origins that need cross-origin access. Production startup fails closed if the PostgreSQL host allowlist is empty. Leave `CORS_ORIGINS` empty only when the browser app and API are served from the same origin. `GROQ_API_KEY` can remain empty when only non-LLM features are needed. Do not put credentials in any `VITE_*` setting; Vite variables are public build-time values.

Production mode rejects the development JWT fallback, missing or invalid encryption keys, wildcard/non-HTTPS CORS origins, private/local hostnames, and an unset CORS setting. API documentation endpoints are disabled in production. Authentication throttling and query-result caching are process-local; run one backend worker/replica unless these controls and caches are moved to shared infrastructure or enforced at a trusted edge. Configure trusted-proxy client IP forwarding and rate limits at the public ingress for multi-instance deployments.

Deployment preflight checklist:

- `APP_ENV=production` with a non-default `JWT_SECRET_KEY` (32+ random characters) and no fallback secret values.
- `CORS_ORIGINS` contains only explicit public HTTPS origins; do not use `localhost`, private ranges, or wildcard origins in production.
- `POSTGRES_ALLOWED_HOSTS` contains only approved public PostgreSQL hostnames or public IPs; reject loopback, private RFC1918, link-local, multicast, metadata, and localhost values.
- `POSTGRES_CREDENTIALS_ENCRYPTION_KEY` is a valid Fernet key and is stored in a secure secret manager or an untracked `.env` file.
- TLS is terminated at a trusted reverse proxy or load balancer, and the app is not exposed directly over plain HTTP.
- Outbound egress is restricted to required DNS, HTTPS, and Postgres endpoints; metadata and private-network destinations are blocked.
- The `.env` file is never committed; production secrets are backed up separately and rotated before reuse.

The backend exposes:

- `GET /api/v1/health` — liveness check.
- `GET /api/v1/health/ready` — readiness check including internal application-database connectivity.

Responses include an `X-Request-ID` for correlating operational reports with server logs. Unexpected errors return sanitized messages; logs record the request identifier and exception type rather than exception text that could contain credentials.

### Docker Compose

The production-oriented Compose deployment serves the built static frontend with non-root Nginx, proxies `/api/` to a non-root FastAPI container, runs Alembic migrations before starting one Uvicorn worker, and persists the internal SQLite database and uploaded files in the `databy_data` named volume. The backend is not published directly. Nginx supports API streaming and limits request uploads. The host-facing Nginx port is HTTP; terminate TLS at a trusted HTTPS load balancer or reverse proxy and do not expose this service publicly over plain HTTP.

Create `.env` from `.env.example`, generate both secrets as described above, set `APP_ENV=production`, set the actual HTTPS CORS origins (or leave it explicitly empty for same-origin access), and then run from the project root:

```powershell
docker compose config
docker compose up --build -d
docker compose ps
Invoke-WebRequest http://localhost:8080/health
```

The frontend is available on port `WEB_PORT` (8080 by default). Configure the TLS ingress to forward to this port and preserve streaming responses. Docker builds do not copy `.env` into either image. Backend migrations run at container startup; inspect logs with `docker compose logs backend`.

To stop the application without removing persistent data:

```powershell
docker compose down
```

### Backups and restore

Back up the application database and uploaded SQLite files together because the database contains references to those files. Quiesce writes (stop the app or use a consistent SQLite backup procedure), then create an archive from the named volume:

```powershell
docker compose stop backend
docker run --rm -v databy-ai_databy_data:/data -v "${PWD}:/backup" alpine:3.21 `
  tar -czf /backup/databy-ai-data.tar.gz -C /data .
docker compose start backend
```

Compose may prefix the volume name with the project name; inspect it with `docker volume ls` and substitute the actual name. Store backups encrypted and separately from the deployment. To restore, stop the backend, extract a trusted archive into the same named volume while mounted in a temporary container, verify ownership/permissions, and start the backend. Keep the matching encryption key and uploaded files with the backup; without the key, encrypted PostgreSQL credentials cannot be recovered.

### Security and operational limitations

Do not expose the application publicly until production secrets, HTTPS, exact CORS origins, trusted proxy configuration, PostgreSQL least-privilege accounts, outbound network controls, and ingress rate limiting are configured. PostgreSQL targets must match the configured exact-host allowlist; every DNS answer is checked, non-global and known cloud-metadata addresses are rejected, and the selected validated IP is pinned with `hostaddr` while retaining the hostname for TLS verification. The destination is resolved and checked again immediately before each new driver connection, preventing DNS rebinding from changing the socket destination after validation. Application checks are defense in depth, not a substitute for egress firewalling.

For production network policy, apply default-deny egress to the backend. Permit DNS only to the deployment's trusted resolver, HTTPS only to required provider endpoints such as `api.groq.com` when Groq is enabled, and PostgreSQL TCP (`5432`, or the explicitly configured destination port) only to the public IPs currently resolved for configured database hosts. At minimum, deny IPv4 `0.0.0.0/8`, `10.0.0.0/8`, `100.64.0.0/10`, `127.0.0.0/8`, `169.254.0.0/16`, `172.16.0.0/12`, `192.0.0.0/24`, `192.0.2.0/24`, `192.88.99.0/24`, `192.168.0.0/16`, `198.18.0.0/15`, `198.51.100.0/24`, `203.0.113.0/24`, `224.0.0.0/4`, and `240.0.0.0/4`; deny IPv6 `::/128`, `::1/128`, `::ffff:0:0/96`, `64:ff9b::/96`, `64:ff9b:1::/48`, `100::/64`, `2001::/23`, `2001:db8::/32`, `2002::/16`, `3fff::/20`, `fc00::/7`, `fe80::/10`, and `ff00::/8`, plus any additional special-purpose ranges in the current IANA registries. Explicitly block provider metadata destinations including `169.254.169.254`, `100.100.100.200`, and `168.63.129.16`, and all internal service/network ranges. Reconcile dynamic database DNS/IPs with firewall rules; do not allow broad private-network exceptions. Docker Compose does not implement these egress ACLs itself, so enforce them in the host/cloud firewall or an egress proxy before public deployment. Do not claim complete SSRF protection without verifying that network policy.

The in-process authentication limiter can be bypassed across multiple workers/replicas and can see proxy addresses instead of end-user addresses unless forwarding is correctly configured. The Compose backend command is fixed at one Uvicorn worker and Compose declares one backend replica. Do not scale the service or run multiple workers: auth throttling, SQL concurrency limits, connection-engine caches, and result caches are process-local. A backend restart clears temporary query results; users must rerun queries to restore analytics/export availability. PostgreSQL read-only transactions and SQL validation cannot guarantee that every user-defined database function has no external side effects; use least-privileged database roles.
